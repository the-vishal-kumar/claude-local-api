# claude-local-api

A tiny, dependency-free HTTP service that turns your **Claude subscription**
into a local API endpoint. You `POST` a task; Claude reads files, runs commands,
and edits code in a working directory you choose; you get the structured result
back as JSON.

> **Single-user tool.** Subscription (OAuth) credentials are licensed for
> individual use. Run this locally for your own automation. Do **not** expose it
> as a shared, multi-user service.

> **Learning project.** This repository is published so others can read and
> study it. It is **not** open source — see [License](#license) before doing
> anything other than learning from it.

## Problem Statement

You already pay for a Claude Pro/Max subscription and you want to drive Claude
**programmatically** from your own scripts and tools — not click around a chat
window. But:

- The raw Anthropic API uses a **separate, metered API-key account**, so calling
  it does **not** draw on the subscription you already pay for.
- There is **no official Go Agent SDK**, so there is no first-class way to embed
  an agent in a Go program.
- The Claude Code CLI _can_ run non-interactively, but wiring it into other
  tools means everyone re-invents argument building, timeouts, JSON parsing, and
  the subtle billing footguns by hand.

## Solution

`claude-local-api` is a small Go HTTP server that drives the **Claude Code CLI**
in non-interactive ("headless") mode (`claude -p --output-format json`) on your
behalf. Shelling out to the CLI is the supported way to use Claude
programmatically from Go — and, unlike a raw API key, it bills against the
subscription you already have.

- 🧩 **One endpoint.** `POST /v1/run` with a prompt; get a JSON result back.
- 🖼️ **Multimodal in.** Upload images, PDFs, or any files (multipart **or**
  base64) for the agent to read and process.
- 🎛️ **Formats per request.** Ask for Markdown / HTML / CSV / plain text, or
  **schema-validated structured JSON**.
- 📤 **Files out.** Get generated images, PDFs, archives, or any file the agent
  produced back — inline base64, `multipart/mixed`, or a `zip` bundle.
- 🔒 **No shell, no injection.** The prompt and every flag are passed as discrete
  `argv` elements — never through a shell. Uploads land in a sandboxed,
  traversal-guarded per-request workspace.
- 💳 **Subscription-safe by default.** Strips `ANTHROPIC_API_KEY` /
  `ANTHROPIC_AUTH_TOKEN` so a stray key can't silently bill you metered rates.
- ⏱️ **Bounded.** Per-task timeouts, body/upload/output caps, and graceful
  shutdown.
- 🧪 **Testable seam.** The HTTP layer depends on `Runner` + `Workspace`
  interfaces, so handlers are tested against fakes — no CLI required.
- 📦 **Zero third-party Go deps.** Standard library only: fast, offline-friendly,
  easy to audit.
- 📖 **Self-documenting.** Swagger UI at `/docs` and an OpenAPI spec at
  `/openapi.json`, generated by reflecting over the code — no hand-written spec.
- 🐳 **Batteries-included image.** A multi-stage image bundles the server, the
  CLI, **and** a media/data toolchain (Python, ffmpeg, ImageMagick, pandoc) so
  the agent can actually generate files.

## How it works

```
HTTP client ──POST /v1/run──► claude-local-api ──exec──► claude -p ──► result JSON
   (curl, app)                  (this service)         (Claude Code CLI)
```

The service is transport-only. It validates the request, enforces a timeout,
invokes the CLI with the prompt and flags as **discrete arguments**, parses the
CLI's JSON envelope, and returns it.

## Prerequisites

1. **Go 1.22+** — to build the service (only needed for the local, non-Docker
   path).
2. **Claude Code CLI**, installed and logged in to your subscription:
   ```bash
   npm install -g @anthropic-ai/claude-code
   claude          # run /login once and sign in with your Pro/Max account
   ```
   Verify it works non-interactively:
   ```bash
   claude -p "say hello" --output-format json
   ```

For the Docker path you only need **Docker** (Node.js, Go, and the CLI all live
inside the image).

## Initial setup

```bash
# Clone the repository (for personal study — see the License).
git clone https://github.com/the-vishal-kumar/claude-local-api.git
cd claude-local-api

# Build.
make build          # produces ./bin/claude-local-api

# Run.
./bin/claude-local-api
# time=... level=INFO msg=listening addr=:8787 force_subscription=true permission_mode=acceptEdits task_timeout=5m0s
# (Logs are text by default; set CLAUDE_JSON_LOGS=true for JSON — the Docker image already does.)

# Call it (in another terminal).
curl -s -X POST localhost:8787/v1/run \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"summarize README.md and list any TODOs","cwd":"/path/to/repo"}'
```

## Run with Docker

The image is **multi-stage** and **batteries-included**: a Go stage compiles the
server, and a Node.js runtime stage installs the Claude Code CLI _plus_ a
media/data toolchain (Python+matplotlib/Pillow, ffmpeg, ImageMagick,
ghostscript, pandoc, zip). The CLI is required because the service shells out to
it; the toolchain is required so the agent can actually **generate** files
(charts, images, video, PDFs, archives). Expect a large image (~2 GB).

**Two `make` commands — authenticate once, then start:**

```bash
make token        # ONE-TIME: authorize in your browser; the token is saved to .env for you
make start        # build (if needed) + start; prints http://localhost:8787/docs
```

After that, day-to-day is a single command:

```bash
make start        # start / restart
make stop         # stop
make logs         # follow logs
```

Verify and call it:

```bash
curl -s localhost:8787/healthz
curl -s -X POST localhost:8787/v1/run \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"say hello"}'
```

> **Why two steps the first time?** Subscription auth is OAuth — there's no
> password or key to "just paste," so `make token` has you authorize once in a
> browser, then mints a long-lived **`CLAUDE_CODE_OAUTH_TOKEN`** (bills your plan,
> not metered rates) and writes it into `.env` for you. From then on `make start`
> is non-interactive — no per-machine `/login`, portable to CI. (`.env` is
> git-ignored, so the token is never committed.) Alternatives: `make login` for
> the interactive `/login` (persisted in the `claude-home` volume, no `.env`
> needed); or for **zero** interactive steps, put a metered `ANTHROPIC_API_KEY`
> in `.env` and set `CLAUDE_FORCE_SUBSCRIPTION=false`.

Point `./workspace` at a repo you want the agent to edit in place (optional —
file uploads/outputs use ephemeral workspaces and don't need it).

> **Linux note.** The container runs as a non-root user (uid `10001`), so the
> host `./workspace` directory must be writable by that uid — otherwise the
> agent's `Edit`/`Bash` file writes fail with _permission denied_. Fix it once
> with `chown -R 10001 ./workspace` (or `chmod -R a+rwX ./workspace`). On Docker
> Desktop (macOS/Windows) the file-sharing layer handles this for you.

The shipped [`docker-compose.yml`](./docker-compose.yml) defaults to the **safe**
`CLAUDE_PERMISSION_MODE=acceptEdits`, so unattended tasks can't run arbitrary
`Bash` against your mounted `./workspace` repo. For **file generation** (which
needs `Bash` to run python/ffmpeg/etc.), send `"permission_mode":"bypassPermissions"`
**per request** — those requests carry file outputs and therefore run in the
isolated, ephemeral `/runs` workspace, never your mounted repo (see
[Permission modes & safety](#permission-modes--safety)).
Ephemeral workspaces live on a container-internal `claude-runs` volume
(`/runs`), so they don't depend on the host bind-mount permissions.

## Configuration

All configuration is read from the environment at startup. Every variable is
optional; defaults are shown.

| Variable                    | Default          | Description                                                   |
| --------------------------- | ---------------- | ------------------------------------------------------------- |
| `CLAUDE_API_ADDR`           | `:8787`          | TCP address to listen on.                                     |
| `CLAUDE_BIN`                | `claude`         | Name or path of the Claude Code executable.                   |
| `CLAUDE_DEFAULT_CWD`        | `.`              | Working directory used when a request omits `cwd`.            |
| `CLAUDE_ALLOWED_TOOLS`      | `Read,Edit,Bash` | Default tool allow-list (`--allowedTools`).                   |
| `CLAUDE_PERMISSION_MODE`    | `acceptEdits`    | Default permission mode (see below).                          |
| `CLAUDE_EXTRA_ARGS`         | _(empty)_        | Extra CLI flags appended to every task, whitespace-separated. |
| `CLAUDE_TASK_TIMEOUT`       | `5m`             | Max duration of one task (Go duration string).                |
| `CLAUDE_MAX_BODY_BYTES`     | `1048576`        | Max request body size in bytes.                               |
| `CLAUDE_FORCE_SUBSCRIPTION` | `true`           | Strip API-key env vars so tasks bill the subscription.        |
| `CLAUDE_JSON_LOGS`          | `false`          | Emit JSON logs instead of text.                               |

Workspace / file I/O (used by the multimodal request path):

| Variable                        | Default            | Description                                                       |
| ------------------------------- | ------------------ | ----------------------------------------------------------------- |
| `CLAUDE_WORKSPACE_ROOT`         | _temp dir_ (`/runs` in image) | Root for ephemeral per-request working directories.    |
| `CLAUDE_WORKSPACE_EPHEMERAL`    | `true`             | File requests without `cwd` get a fresh auto-managed workspace.   |
| `CLAUDE_KEEP_WORKSPACE`         | `false`            | Keep ephemeral workspaces after the request (debugging).          |
| `CLAUDE_WORKSPACE_TTL`          | `1h`               | Sweep orphan `run-*` dirs older than this at startup (`0` = off). |
| `CLAUDE_MAX_UPLOAD_BYTES`       | `26214400` (25 MiB) | Max size of a single uploaded input file.                        |
| `CLAUDE_MAX_UPLOAD_TOTAL_BYTES` | `104857600` (100 MiB) | Max size of an entire multipart request body.                  |
| `CLAUDE_MAX_INPUT_FILES`        | `32`               | Max number of input files per request.                            |
| `CLAUDE_MAX_OUTPUT_BYTES`       | `52428800` (50 MiB) | Max size of a single returned output file.                       |
| `CLAUDE_MAX_OUTPUT_TOTAL_BYTES` | `209715200` (200 MiB) | Max aggregate size of all returned outputs.                    |
| `CLAUDE_MAX_OUTPUT_FILES`       | `64`               | Max number of returned output files.                              |

See [`.env.example`](./.env.example) for a copy-paste template. **With Docker,
`docker compose` loads `.env` automatically** (via `env_file`), so editing
`.env` configures the container. The three Docker-structural values
(`CLAUDE_API_ADDR`, `CLAUDE_DEFAULT_CWD`, `CLAUDE_WORKSPACE_ROOT`) are pinned in
`docker-compose.yml` and ignore `.env`. The **bare binary** (non-Docker) does
not read `.env` itself — export the vars (e.g.
`env $(grep -v '^#' .env | xargs) ./bin/claude-local-api`).

## API

### `POST /v1/run`

Execute a single task.

Accepts **`application/json`** or **`multipart/form-data`** (a `request` part
holding this JSON, plus file parts). Unknown JSON fields are rejected.

| Field             | Type     | Required | Description                                                        |
| ----------------- | -------- | -------- | ------------------------------------------------------------------ |
| `prompt`          | string   | yes      | The instruction for the agent.                                     |
| `cwd`             | string   | no       | Working directory; overrides `CLAUDE_DEFAULT_CWD`.                 |
| `allowed_tools`   | string   | no       | Tool allow-list; overrides `CLAUDE_ALLOWED_TOOLS`.                 |
| `permission_mode` | string   | no       | Permission mode; overrides `CLAUDE_PERMISSION_MODE`.               |
| `session_id`      | string   | no       | Resume a previous session (use the `session_id` you got).          |
| `model`           | string   | no       | Model for this task (`--model`), e.g. `opus`, `sonnet`.            |
| `effort`          | string   | no       | `low`\|`medium`\|`high`\|`xhigh`\|`max` (`--effort`).              |
| `max_budget_usd`  | number   | no       | Cap spend on this task (`--max-budget-usd`).                       |
| `add_dirs`        | string[] | no       | Extra directories the agent may access (`--add-dir`).             |
| `content_format`  | string   | no       | `markdown`\|`html`\|`csv`\|`text`\|`json` — shapes the answer.    |
| `json_schema`     | object   | no       | JSON Schema; the answer is validated against it and returned in `structured`. |
| `inputs`          | array    | no       | Inline files: `[{"path","content_base64"}]` staged into the workspace. |
| `output`          | object   | no       | `{"return_all":bool,"globs":[...]}` — which generated files to return. |
| `delivery`        | string   | no       | `json`\|`multipart`\|`zip` (or set via the `Accept` header).      |

See [Multimodal inputs, formats & file outputs](#multimodal-inputs-formats--file-outputs)
for full details and examples.

**Example**

```bash
curl -s -X POST localhost:8787/v1/run \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"say hello"}'
```

**Response** `200 OK` — the CLI's result envelope:

```json
{
  "type": "result",
  "subtype": "success",
  "result": "Hello! ...",
  "session_id": "sess_demo_123",
  "total_cost_usd": 0.0042,
  "is_error": false,
  "duration_ms": 1180,
  "duration_api_ms": 900,
  "num_turns": 2
}
```

Continue the conversation by sending the returned `session_id` back in the next
request.

**Errors** are JSON: `{"error": "..."}`.

| Status | When                                                              |
| ------ | ----------------------------------------------------------------- |
| `400`  | Malformed JSON, unknown field, missing `prompt`, bad enum/schema, unknown `delivery`, or no `request` part. |
| `405`  | Wrong method for the route.                                       |
| `413`  | Request body exceeded the size cap.                               |
| `415`  | Unsupported `Content-Type`.                                       |
| `501`  | File I/O features requested but the workspace is not configured.  |
| `502`  | The CLI failed or returned unparseable output.                    |
| `504`  | The task exceeded `CLAUDE_TASK_TIMEOUT`.                          |

When a JSON schema or generated files are involved, the `200` envelope also
carries `structured` (the parsed schema object) and/or `artifacts` (see below).

> A `200` with `"is_error": true` means the agent produced a valid result but
> ended abnormally (for example, hit a turn limit). Inspect `subtype`.

### `GET /healthz`

Liveness check. Returns `200` with `{"status":"ok"}`.

### `GET /docs` and `GET /openapi.json`

Interactive **Swagger UI** at [`/docs`](http://localhost:8787/docs), backed by an
**OpenAPI 3.0** document at `/openapi.json`. The spec is **generated at startup
by reflecting over the Go request/response types**, so it tracks the code — add
a field to `claude.Request` and it appears in the docs automatically; there is
no hand-maintained spec and no codegen step (still zero third-party deps).
`/docs` loads the Swagger UI assets from a CDN, so viewing it needs internet
access (the spec itself is served locally).

## Multimodal inputs, formats & file outputs

This is what makes `/v1/run` feel like the chat window — over your subscription,
via the CLI.

> **How file _generation_ really works.** Claude (through the CLI) does **not**
> natively render images or video. It **generates files by writing and running
> code** — e.g. a Python script that emits a PNG, `ffmpeg` for video, `zip` for
> archives. So "give me a chart/PDF/video" works **only if the container has
> that toolchain**, which is exactly why the Docker image is batteries-included
> (Python+matplotlib/Pillow, ffmpeg, ImageMagick, ghostscript, pandoc). On a
> bare local build you only get what's already on your `PATH`. File generation
> also needs the agent to run `Bash`/`Write`, so pass
> `"permission_mode":"bypassPermissions"` per request — such requests run in the
> isolated, ephemeral `/runs` workspace, not your mounted repo.

### Sending files in

**Multipart** (best for real/binary files):

```bash
curl -s -X POST localhost:8787/v1/run \
  -F 'request={"prompt":"Describe image.png and transcribe any text in report.pdf"};type=application/json' \
  -F 'file=@image.png' \
  -F 'file=@report.pdf'
```

**Base64 inline** (best for small, programmatic payloads):

```bash
curl -s -X POST localhost:8787/v1/run -H 'Content-Type: application/json' -d '{
  "prompt": "Summarize data.csv",
  "inputs": [{"path":"in/data.csv","content_base64":"YSxiCjEsMgo="}]
}'
```

Uploaded files are staged into a per-request **workspace** (a fresh directory),
and the agent is told they're there. Multipart files land under `in/<filename>`.

### Defining the response format

- `content_format`: `markdown` | `html` | `csv` | `text` | `json` — appended as
  an instruction to the agent.
- `json_schema`: a JSON Schema object. The CLI validates the final answer
  against it (`--json-schema`); the parsed object is returned under
  `structured`:

```bash
curl -s -X POST localhost:8787/v1/run -H 'Content-Type: application/json' -d '{
  "prompt": "Extract the invoice total and currency.",
  "json_schema": {"type":"object","properties":{"total":{"type":"number"},"currency":{"type":"string"}},"required":["total","currency"]}
}'
# -> { ..., "result": "{\"total\":42.0,\"currency\":\"USD\"}", "structured": {"total":42.0,"currency":"USD"} }
```

### Getting generated files back

The agent writes deliverables into an `outputs/` directory in its workspace; the
service collects them and returns them. Control collection with `output`
(`{"return_all":true}` is the default; add `"globs":["*.pdf"]` for files outside
`outputs/`). Choose how they're delivered with `delivery` or the `Accept` header:

| `delivery` / `Accept`        | Response                                                            |
| ---------------------------- | ------------------------------------------------------------------ |
| `json` *(default)*           | One JSON envelope; each file inline as `artifacts[].content_base64`. |
| `multipart` / `multipart/mixed` | First part = JSON envelope (metadata only); then one raw part per file. |
| `zip` / `application/zip`    | An `application/zip` containing `result.json` + every file at its path. |

```bash
# "Plot y = x^2 and return the PNG", delivered as a zip. bypassPermissions lets
# the agent run python unattended; it runs in the isolated ephemeral workspace.
curl -s -X POST localhost:8787/v1/run -H 'Accept: application/zip' -H 'Content-Type: application/json' -d '{
  "prompt": "Plot y=x^2 for x in [-10,10] and save it to outputs/plot.png",
  "permission_mode": "bypassPermissions"
}' -o result.zip
unzip -l result.zip      # result.json + outputs/plot.png
```

The JSON envelope's `artifacts[]` entries carry `path`, `media_type`, `size`,
and (for `json` delivery) `content_base64`.

### Limits & lifecycle

Uploads and outputs are capped (count + per-file + total bytes — see
[Configuration](#configuration)). Ephemeral workspaces are created per request
and deleted afterward (set `CLAUDE_KEEP_WORKSPACE=true` to keep them). Supplying
an explicit `cwd` runs in place instead and is never deleted.

## Permission modes & safety

`permission_mode` controls what the agent may do without prompting (there is no
human to approve prompts in headless mode):

- `default` — normal CLI prompting rules; in headless mode this can stall on any
  action that would otherwise ask for approval.
- `acceptEdits` _(default)_ — auto-approves **file edits**. Other actions may
  still require approval and therefore stall a non-interactive run.
- `plan` — plans without making changes.
- `dontAsk` — runs pre-approved tools only.
- `bypassPermissions` — **skips all checks**, including arbitrary `Bash`. Only
  use this inside a sandbox/container or on a repo you can throw away. This is
  the most powerful and the most dangerous mode.

If you want fully unattended shell execution, you generally need
`bypassPermissions` — so isolate the process accordingly. Running in the
provided Docker container is one such isolation boundary.

## Billing notes you should not skip

- **Subscription vs. API key are separate accounts.** This service is built to
  use your subscription via the CLI's OAuth login.
- **An exported `ANTHROPIC_API_KEY` silently wins over your subscription
  login** — you would quietly pay metered API rates. To prevent this, the
  service strips `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` from the CLI's
  environment by default (`CLAUDE_FORCE_SUBSCRIPTION=true`). Set it to `false`
  only if you *intend* to use an API key.
- **Billing change on June 15, 2026.** From that date, Agent SDK / `claude -p`
  usage on subscription plans draws from a separate monthly Agent SDK credit
  (you opt in once), not your interactive chat limit. See
  <https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan>.

```bash
make help     # list targets

make test     # go test -race ./...
make build    # ./bin/claude-local-api
make all      # fmt + vet + test + build
```

Docker helpers (run `make help` for the full list):


handlers are tested against a fake runner with no CLI involved. There are no
third-party dependencies — only the Go standard library.
